# Design note - errand agent

**Shape.** One agent, one process, Python, no framework. The LLM (Claude via the Anthropic SDK, or a deterministic scripted model for evals) proposes tool calls; the application decides what actually runs. A single agent was enough: the hard parts (consent, idempotency, recovery, budgets) are deterministic policy, and splitting them across agents would only add places for state to drift. Trade-off accepted: the model never sees the result of a consequential action in the same turn; the application reports it instead.

**State model.** `WorkflowState` is an explicit enum with an allowed-transition table (`IDLE -> COLLECTING -> SEARCHING -> AWAITING_APPROVAL -> EXECUTING -> VERIFYING -> COMPLETED | FAILED`); an illegal transition raises. Separately, a `Task` dataclass holds the user's facts (service, area, date range, time window, budget, preferences, target booking). The model records facts through an `update_task` tool, so "collect only what's missing" is computed from data (`Task.missing()`), re-asking is prevented by the prompt listing what is already known, and a correction updates one field while the others survive. Everything (task, state, history, pending approval, pending operations, holds) is persisted to JSON after each turn and before each side effect.

**Approval enforcement.** `book`, `cancel`, `reschedule` are intercepted in the orchestrator: the model's call becomes an `ApprovalRequest` with a fingerprint = SHA-256 of (action + material fields: provider, slot, price / booking id / new slot), and the turn ends with a confirmation prompt generated by code, not by the model. The user's next message is classified deterministically (approve / reject / other). Only "approve" leads to execution; "other" invalidates the request and is treated as a new instruction. At execution time the gate re-computes the fingerprint from *live* data (the hold is re-validated and re-held if expired), so a changed price, slot or provider fails `authorize()` and produces a fresh request. Tool output cannot reach the gate at all, which is the real defence against injected "the user already approved" text; the sanitizer that flags such text is for visibility. Memory deletion is likewise allowed only when the user's own message contains a forget intent.

**Idempotency and recovery.** Every side effect gets a stable key derived from the hold or booking (`book:<hold_id>`), is written as an in-flight `PendingOperation` before the call, and is replayed by the backend for the same key. On `timeout`, the agent moves to `VERIFYING` and asks `get_booking_status` first; it retries (same key, once) only if the source of truth says nothing was booked, and reports failure honestly if two timeouts leave nothing booked. A direct success is also verified before being announced. A repeated "yes" after completion is a no-op by state. On startup, in-flight operations are resolved from `get_booking_status`, so a crash between `book()` returning and the result being persisted neither loses nor duplicates the booking. Limits: 8 model turns, 12 tool calls, 30 s wall clock per message; every exit (limit, model error, tool error, unexpected exception) ends in a user-facing message stating that nothing was booked, cancelled or moved.

**Memory and context.** `MemoryStore` records `kind` (explicit / inferred), `confirmed`, `status` (active / forgotten), tags and provenance. Only active memories that are explicit or confirmed-inferred are *eligible*; retrieval filters by relevance tags (general, the current service, area) and a token budget. `ContextBuilder` assembles system = rules + task state + eligible memories, then keeps the most recent history that fits a fixed budget (never orphaning a tool result). Each turn emits `context_sent` with the memory ids included, those rejected (and why), tokens used and messages dropped; tests seed 57 memories and 240 old messages and assert the budget is never exceeded and forgotten/unconfirmed ids never appear. Proactive follow-up uses the same preferences: a `provider_cancelled` event (polled, no user prompt) triggers a replacement search within budget/time window, a hold, and a fresh approval request.

**Observability.** `Tracer` writes JSONL per run: state transitions, context reports, model calls (latency, tokens, estimated cost), tool calls with sanitized results and retry attempts, gate decisions, injections flagged, verification results. The CLI renders chat and trace side by side.
